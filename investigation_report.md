## Root Cause Analysis

### Code Location
**File**: `app/api/firebase.py`
**Function**: `add_pocket_article()`
**Lines**: 108-113

### ID Generation Logic

```python
# Generate item_id from URL (sanitize for use as key)
from core.utils import sanitize_filename
import hashlib

url_hash = hashlib.sha256(data.url.encode()).hexdigest()[:12]
item_id = f"pocket_{url_hash}"
```

**How it works**:
1. Takes SHA-256 hash of the URL
2. Extracts first 12 characters of the hex digest
3. Prefixes with `"pocket_"`

**Example**:
- URL: `https://medium.com/@marius.kamp/...`
- SHA-256: `ca40716ee736...`
- item_id: `pocket_ca40716ee736`

## Impact Assessment

### ✅ No Data Corruption

- **Real Pocket articles remain intact** with their original numeric item IDs
- The `pocketarticle` table has 21,203 entries with proper IDs
- No existing Pocket item_ids were renamed or modified

### ⚠️ Potential Issues

1. **ID Collision Risk**: If two different URLs hash to the same first 12 characters, there could be a collision (extremely unlikely but theoretically possible)

2. **Inconsistent ID Format**: The system now has two types of article IDs:
   - **Real Pocket IDs**: Numeric strings (e.g., `"4030377064"`)
   - **Firebase API IDs**: `pocket_` prefix with 12-char hash (e.g., `"pocket_ca40716ee736"`)

3. **Firestore Sync Confusion**: The 112 articles fetched from Firebase and pushed to htbase.archivist.lol likely had their original item_ids, but when saved through this endpoint, they would get new `pocket_*` IDs

## Recommendations

### 1. **Use Original item_ids When Available** ⭐

When articles are synced from Firebase that already have item_ids, preserve those IDs instead of generating new ones:

```python
# Proposed change in /firebase/add-pocket-article
if data.pocket_data and 'item_id' in data.pocket_data:
    item_id = data.pocket_data['item_id']  # Use original ID
else:
    url_hash = hashlib.sha256(data.url.encode()).hexdigest()[:12]
    item_id = f"pocket_{url_hash}"  # Generate only if needed
```

### 2. **Document the ID Generation Strategy**

Add clear documentation explaining:
- When `pocket_*` IDs are generated
- Why they're different from real Pocket IDs
- How to distinguish between ID types

### 3. **Consider Using URL-Based Deduplication**

The `archived_urls` table has a **unique constraint on URL**, which prevents duplicates. This is good! But ensure that:
- The endpoint checks if a URL already exists before creating a new entry
- If it exists, return the existing item_id instead of generating a new one

### 4. **Monitor for ID Collisions**

While SHA-256 truncation to 12 characters gives 16^12 = 281 trillion possibilities, implement:
- A check to detect if a generated ID already exists
- Fallback logic to handle collisions (e.g., add a suffix)
